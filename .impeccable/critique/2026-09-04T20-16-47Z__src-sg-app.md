# Design Specificity Verdict

Specific in the templates and the copy. Generic in the shell and the card.

Only this product: eight repo colours handed out in load order, because one push interleaves four SVN working copies. File lists cut by working copy, because commits cut by working copy. A revision row that drops the revision number, because the message is what you scan.

Liftable into any tool: the shell is the default WinUI sample composition — NavigationView, Mica, cards, a bottom console. The worktree card is a generic item with badges and buttons. The relationship that defines the product — branch, born from a snapshot, N behind, M ahead — is a caption sentence built in code. DESIGN.md:78 draws that bridge in ASCII. The GUI never draws it.

Deterministic scan: NO SIGNAL. The detector returned 30 findings, all false positives — 29 in vendored Monaco and its build-output copy, 1 in a WinUI SDK asset. It cannot parse XAML: pointed at MainWindow.xaml it returns [] with exit 0, a silent no-op. It also ran degraded, with its HTML parser modules missing. Every measurement here is hand-taken.

No visual overlay: native app, no URL, no page to inject into.

# Overall Impression

The craft is real and it is in the small: a density token block the skeleton loader reads at runtime, so loading and loaded geometry cannot drift. Tooltips that explain mechanism. A light palette re-derived rather than inverted.

The problem is one level up. Every card presents its actions as a flat, equal-weight row that cannot wrap, inside a window that clips. The app knows far more about each worktree than it shows — ahead, behind, dirty, pending, missing are all on the row — and spends that knowledge on chips rather than on deciding what to do next.

Biggest opportunity: let state choose the primary action. The pattern already exists one card up, where Sync goes accent only when the checkout is behind.

# What's Working

1. The density system is real, and the skeleton proves it. Templates.xaml:112 declares row height, font size, icon size, spacing and padding once. Skeleton.xaml.cs reads the same resources at runtime, so loading and loaded geometry are identical and nothing reflows.
2. The push preflight turns the scariest property of the product into a readable pre-state. Six checks before the button goes live, collapsed to one green line when they pass.
3. Hygiene is clean. Zero hex colours outside the theme dictionaries. All three themes define the same 31 keys. All 69 click handlers carry a name or tooltip.

# Priority Issues

## [P1] Action and status rows cannot wrap, inside a window that clips
Three horizontal StackPanels in the overview hold 9, 7 and 6 children (MainWindow.xaml:164, :130, :184). The 9 is a branch name, size text and up to six status chips. They sit inside a ScrollViewer (MainWindow.xaml:98) with no horizontal scrollbar, so WinUI clamps to viewport width and clips with no recovery. MainWindow is the narrowest primary window at 1280. No WrapPanel exists anywhere in the app; no minimum window width is set.
Why: behind + dirty + pending together is normal, not an edge case.
Fix: wrap the chip row; give button rows one primary, two secondary, rest behind the existing overflow menu.
Command: /impeccable layout

## [P1] Removing a branch never mentions the commits it destroys
MainWindow.xaml.cs:783-787. Confirmation branches on Dirty only; the call passes force: true unconditionally, bypassing the core guard. Ahead is on the row already.
Why: the only action that permanently destroys local work has the weakest confirmation in the app.
Fix: build the text from Ahead, Dirty, Pending. Require acknowledgement when Ahead > 0. Stop hardcoding force.
Command: /impeccable harden

## [P1] A long push loses its own log to the overview's background poll
Session.Log is one static sink; Runner.Run and Runner.Quiet both reassign it. The overview polls every 2 minutes through Runner.Quiet.
Why: a monorepo push takes minutes. Two minutes in, the Push window's log stops updating silently.
Fix: stop Runner.Quiet touching the sink; have Runner.Run save and restore rather than overwrite.
Command: /impeccable harden

## [P1] The push preflight names problems it refuses to let you fix
PushWindow.xaml:72-90 renders failing checks through an ItemsControl — nothing clickable.
Why: highest-frequency loop in the tool. Every blocked push costs a close, a hunt, a second window, a reopen.
Fix: make each failing check an action row (uncommitted changes -> Open commit; behind -> Rebase now), then re-run the preview in place.
Command: /impeccable shape

## [P2] The accent button carries no information, and two primaries appear together
MainWindow.xaml:194 gives Push to SVN AccentButtonStyle with no binding. Line 192 gives Resolve conflicts the same. During a stopped rebase both are visible and Push cannot succeed.
Why: six worktrees means six equally blue Push buttons; accent stops meaning "do this next".
Fix: bind Push's style the way SyncButton's already is. One primary per card, chosen from state.
Command: /impeccable layout

# Persona Red Flags

Alex (power user, daily): worktree cards are an ItemsControl — not selectable, not focusable, no keyboard nav, no default action; Tab walks 5-6 buttons per card. Every file list has Ctrl+F; checkouts and worktrees, the two lists that grow, have none. No window geometry persistence. No window deduplication — two live Push windows on one branch. 170px of 820 on a console that is empty between operations.

Sam (accessibility): measured good — every click target has a name or tooltip; all three themes carry the same 31 keys. Structural gaps — cards unreachable by keyboard; 26px rows at 12px text, below Fluent's compact minimum; in High Contrast all eight repo colours collapse to one and backgrounds go transparent, so the SVN log's repository tag loses its only visual separator.

Agent operator (project-specific): DESIGN.md decision 25 says agents work in worktrees and humans push. The UI does not know that. Every worktree card is identical whether an agent ran in it for an hour or it was made five minutes ago. "Ready for your review" is the state this product is built around and is not a state a card can wear.

# Minor Observations

1. Glyph E70F carries four meanings (Changes, local-edits chip, uncommitted chip, Open in editor, Edit x2). E73E carries three.
2. "Update and restart" uses E898, the outgoing glyph. Elsewhere E898 means going to SVN, E896 means incoming. An update is incoming.
3. The "nothing to push, idle" chip uses the trash glyph, standing among five genuine alarms. A recommendation dressed as a status.
4. Peak-end failure after a successful push: the result bar says "Pushed.", then the reload re-previews the empty branch and raises a yellow "Nothing to push" warning.
5. Font tokens half-adopted: literal 12 appears 21 times while the two tokens equal to 12 are referenced 7 times. Eight sizes match no token; 15 is off the Fluent ramp.
6. Demoted from Assessment A's priority list: the three unlabelled pane-header icons as a first-timer barrier. DESIGN.md decision 2 says single user for now, so P3.

# Questions to Consider

1. DESIGN.md draws the bridge as a diagram; the GUI renders it as a caption. What if the overview WERE the picture — one lane per checkout, worktrees positioned by ahead/behind, so "needs rebase" is a distance?
2. If exactly one action per card were allowed to be primary, computed from state the row already holds — does the card still need six buttons?
3. Sync, push and rebase run for minutes. Why is progress a global console welded to the bottom, rather than an activity strip on the card the operation belongs to?
4. The push confirmation says "4 SVN commits". What hurts is that those four are not atomic. Should it show the ordered repository list with a "stops here on failure" marker?
